# Provider-Neutral Delivery Orchestration

The **orchestrator** owns the delivery decision flow but does not edit implementation code. A host may conduct DEFINE and specification conversations remotely, then dispatch the executable plan to installed local or remote harnesses. A human operator acts as Product Owner during initial intent definition and specification refinement; agents execute, verify, audit, and self-correct work in bounded Git worktrees.

1. **DEFINE** — Capture business outcomes, scope, non-goals, constraints, and decision owner. MANDATORY COMPLETION GATE: You MUST create or link the tracker item (`gh issue create`) with type labels (`type:feature`, `type:story`, `type:task`, `type:bug`), add it to the project board (`gh project item-add`), and set status to **`01 Define`** (or `Backlog`) using `gh project item-edit` BEFORE proceeding to Stage 2 (**SPECIFY / GRILL**) or Stage 3 (**PLAN**). Do not generate technical `implementation_plan.md` or dispatch code execution until the GitHub Issue exists. Read [github-pipeline-integration.md](../../references/github-pipeline-integration.md).
2. **SPECIFY / GRILL** — Inspect the target repository and relevant Central and Project Knowledge entries. Challenge contradictions, risks, scope boundaries, and acceptance conditions with the user. Update the tracker specification (`gh issue edit` / `gh issue comment`) and set project board status to **`02 Spec`**. Read `grill-with-context` when source-backed challenge is needed.
3. **PLAN** — Create minimal dependency-aware cohesive delivery slices, not artificial microtasks. Construct a Directed Acyclic Graph (DAG) of cohesive delivery slices with explicit file path boundaries. Publish technical `implementation_plan.md` for the **IMPLEMENT** phase with interactive user review request (`RequestFeedback: true`). Each task packet defines fields in [task-packet.md](references/task-packet.md), including worktree provenance, assigned persona, dependencies, and path boundaries. Read [autonomous-rework-loop.md](references/autonomous-rework-loop.md) for DAG scheduling rules. Set project board status to **`03 Plan`**.
4. **DISPATCH** — Create dedicated feature branch (`gh issue develop`) and Git worktree for each slice. Set project board status to **`04 Execute`** (or `In Progress`). Select and assign the slice to the designated agent persona (`developer`) specified in [agent-personas.md](references/agent-personas.md). The executor retains the slice context end-to-end to understand local code, implement, use TDD where relevant, run and fix the verification loop, and return reviewable diff evidence.
5. **COLLECT / VERIFY** — Collect each executor's change summary, verification result, evidence, and blockers. Run the target repository's deterministic verification gate (e.g. configured verification command in `AGENTS.md`, `just verify`, or test runner). Record verification evidence in `walkthrough.md`. If verification fails, initiate the autonomous rework loop (up to `max_retries: 3`), feeding failure logs directly back to the executor persona. An executor stops and returns the slice when a material boundary issue emerges. Read [autonomous-rework-loop.md](references/autonomous-rework-loop.md).
6. **REVIEW** — Open Pull Request (`gh pr create`) linking `Closes #<id>` and update project board status to **`05 Review`**. Conduct multi-persona review (`quality-engineer`, `solution-architect`, `security-auditor`) auditing TDD assertion strength, DDD domain purity, Hexagonal layer isolation, and OWASP security risks. Update `walkthrough.md` and post PR review comments. Read [agent-personas.md](references/agent-personas.md). If a reviewer returns `CORRECT_EXECUTE` or `CORRECT_PLAN`, re-dispatch autonomously to the executor with correction payload until approved or retry limit (N <= 3) is reached.
7. **SHIP / RETURN** — Once changes pass all verifications and persona reviews, commit the verified changes, push the branch to remote origin (`git push`), and create exactly one durable **Delivery Record** (GitHub Issue / PR reference) for the cohesive delivery slice before publishing its **Review Request** on the short-lived task branch. Update project board status to **`06 Ship`**. Present the work to the Product Owner with interactive merge authorization instructions (`gh pr merge`). Upon merge, the issue auto-closes (`Closes #<id>`) and project item moves to **`07 Improve`** where the `improve` skill captures retrospective learnings. If no follow-up improvement is required, the delivery cycle completes as **Done** (`gh project item-archive`). Executors do not merge, approve, or force-push protected default branches; the user retains merge authority.
