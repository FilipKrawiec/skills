# Entities

Reference constraints for designing Entities, derived from Vaughn Vernon's *Implementing Domain-Driven Design*.

> [!IMPORTANT]
> **Aggregate Roots are Entities:** An Aggregate Root is a specialized Entity. It inherits all rules regarding identity, equality, hash calculation, self-validation, and strict Value-Object field typing.

## 1. Identity Constraints
- **Early vs. Late Identity:**
  - **Early Identity:** Generated before persistence (e.g., UUID/ULID wrapped in a dedicated ID Value Object like `OrderId.of(...)`). Required for event-sourced aggregates or if events containing the ID are published during creation.
  - **Late Identity:** Generated by the database (e.g., auto-increment) upon persistence. Avoid this as it complicates testing and event generation.
- **Immutability:** The identity field must be read-only and immutable. State transitions must never alter it.
- **Equality and Hash:** Entity equality (`equals()`) and hash calculations (`hashCode()`) **must be based exclusively on the unique identifier Value Object**. Other properties must be ignored. Two instances with the same identifier represent the same entity.

## 2. Invariant Validation & Strict Value-Object Attributes
- **Zero Raw Primitives**: All attributes stored in an Entity (e.g., prices, quantities, email addresses, order statuses, timestamps) MUST be typed strictly as Value Objects (e.g., `Money`, `Quantity`, `EmailAddress`, `OrderStatus`, `Timestamp`). Never store raw primitives (`String`, `Double`, `Int`, `Long`, `Boolean`) inside Entities.
- **Self-Validation:** An entity must protect its own invariants and remain valid throughout its lifecycle. Never allow public setters. Throw explicit domain exceptions on violation.
- **Deconstruct Validation:**
  - **Attribute Validation:** Validate individual fields upon construction or within Value Objects using `.of(...)`.
  - **Entity Validation:** Validate multi-attribute business invariants before executing state transitions.
  - **Deferred Validation:** Use a separate validator strategy/object when validation requires complex rules or external resources.

## 3. Behavior and Encapsulation
- **Verbs over Nouns:** Expose state mutations only via intention-revealing domain verbs (e.g., `cancel(reason: CancellationReason)` rather than `setStatus(status: String)`).
- **Value-Object Parameters**: All method parameters passed into domain verbs MUST be Value Objects or Entity identifiers, never raw primitives.
- **Encapsulate Collections:** Never expose mutable collections. Return a read-only list/view of Value Objects or child Entities and expose explicit domain methods to add/remove elements.
- **Identity References:** Never pass a collaborator Aggregate Root as an object parameter. Pass its identifier Value Object (e.g., `CustomerId`) only.
