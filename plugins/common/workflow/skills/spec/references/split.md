# Splitting an issue

Keep related fixes, implementation, tests and docs in one bounded, independently reviewable issue and PR when they can ship together, saving repeated agent, review and coordination costs. Split for a concrete independent outcome, a meaningful dependency (such as a separately useful prerequisite), an authority boundary or a delivery constraint. Record the reason; size, estimate or layer alone is not one. Keep acceptance, quality, independent review and owner-authority gates for every resulting issue and PR. Fold a slice that delivers nothing on its own into the change that uses it. An issue found to need several PRs at such a seam is split into an epic with one-PR sub-issues, never sliced by `Part of` PRs. Its own authority approves the epic. First set `type:epic`, drop its lane and rewrite its body in the epic form, so an interrupted split leaves an epic to slice, not a story to rebuild. Then create its one-PR sub-issues as for an epic slice, each packet within the issue's packet (the run's push checks that copy), with blocked-by links where order matters. A run builds the first sub-issue under its hold, and the epic closes through its close check.
