# Epic evidence protocol, version 2

Store records durably alongside the epic, for example in a linked issue or repository file. Retrieve the current acceptance criteria and all records from that location on every validation; do not reuse cached records or content. Each criterion has a stable nonempty `id`, exact `text`, and boolean `checked`. Exactly one record must match each current criterion; stale or duplicate records fail.

A record has `version: 2`, `criterion` (the exact id and text), `state` (`met`, `unmet`, or `unverifiable`), nonempty `author` and `explanation`, a nonempty `evidence` array, and `verification`. Each evidence reference has a unique nonempty `id`, HTTP(S) `url`, and lowercase hex `sha256`. Unmet or unverifiable records also have a nonempty `nextAction` and HTTP(S) `followUp` URL; they remain incomplete.

The only supported evidence is the complete response body of an HTTP(S) GET. Retrieve each referenced URL afresh, following redirects only to HTTP(S), and accept only a successful response whose entire body was read. Hash the exact response body bytes after HTTP content decoding, before text decoding or normalization, using SHA-256. Supply the validator an `evidence` array with one `{id, url, type: "http-body", bytes: Buffer}` per reference, using the originally referenced URL. Never substitute a cached body, metadata, URL hash, partial response, rendered page, or caller assertion of accessibility. Missing, ambiguous, unsupported, unsuccessful or inaccessible retrieval fails validation. Authenticated evidence is supported only when the caller can retrieve its complete body under this contract; otherwise it fails closed.

An independent reviewer, different from the record author, inspects the criterion and retrieved content and records `verification` with nonempty `reviewer`, the exact `criterion` id and text, and the exact evidence references including their digests. The validator recomputes every digest from the supplied bytes and compares both the record and verification to current content. Any change, even at the same URL, requires new verification. A digest identifies bytes; it does not prove the explanation or outcome true. Callers must ensure reviewer identities and independence are authentic and retrieval is fresh; the validator cannot establish either.

Pass `{criteria, records, evidence}` to `validateEpicEvidence`. Treat `complete: false` and its `issues` as actionable failures; do not close an epic on malformed input, retrieval failure, or an incomplete result. Version 1 records cannot establish content identity and must be reverified as version 2.

## Authenticated verification

Call `resolveEpicVerification({repo, issue, commentId, criterion, evidence, state})` from `epic-attestation.mjs` for each criterion before using its result as the record's `verification`. The resolver fetches origin and reads roles from the fetched default branch, then retrieves all pages of the issue's GitHub comments and the selected comment's GitHub GraphQL edit state. It requires exactly one comment whose JSON body names that criterion id. The body is a JSON object with `version: 1`, `criterion: {id, text}`, `state`, and `evidence: [{id, url, sha256}]`; use the exact current criterion and content references from the version 2 record. The API's comment author, never a name in the body, must equal the configured Reviewer, and the configured implementer must be distinct. It rejects edited comments, including edits within the timestamp's resolution, and missing, deleted, ambiguous, stale, malformed or inaccessible records. A failed fetch or API call throws; treat any exception as incomplete. An attestation is tied to the current criterion and evidence bytes, so post a new comment when the criterion, state, or evidence changes; remove superseded comments before requesting verification. The caller must still freshly retrieve and validate evidence with `validateEpicEvidence`. This component does not close issues or change approval and review gates.
